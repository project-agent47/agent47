# P1b：统一资源入口与版本化项目上下文

## 产品定位与重复问题

Agent47 面向任意用户的日常工作任务自动化和智能化，而不是以代码仓库为中心的 IDE。本增量将原“成果库”改成“资源库”：成果是资源的一种来源，项目是归类与固定引用关系，不是另一份正文仓库。

- 全局资源库、项目右侧列表和输入区 `@ 资源` 共用 `ResourceBrowser`。同一资源可查看、引用或固定，不再分别维护资料管理与成果管理页面。
- 已保存的应用成果与其项目固定关系合并为一行。新的、留有 hash/bytes 回执的项目文件写入也纳入成果来源；同一文件版本固定到项目后合并显示。
- “目录文件”按授权目录逐层浏览；“全部／成果／固定材料”是已有成果和固定关系的投影，不是全磁盘索引。旧文件操作记录没有 hash/bytes 的，不伪造回执或自动回填，仍可从目录或原轮次查看。
- 同一来源的不同版本可以保留为不同记录；历史快照、来源证据、消息引用不是应该删掉的重复内容。相同文件名不作为去重依据。

## 项目说明与固定材料

- 项目说明最多 6000 个 JavaScript 字符单元，以 revision 和 SHA-256 留档。它表达用户的目标、语气和输出偏好，不授予工具权限，也不证明事实。
- 固定材料最多 10 份、合计 5 MB，单份最多 1 MB。实际正文沿用 `tasks.db/material_versions`；`projects.db/project_context` 只保存引用 ID、来源标识和版本关系。同一来源、同一 hash 跨项目固定会复用一个版本正文。
- 新任务显示该项目固定版本的待发送 chips，用户可逐条“本次不引用”；点击开始才绑定所显示的版本。服务端校验显示的项目上下文 revision 与 pin IDs，过时选择会要求重选。
- 固定后不会跟随源文件变化。显式“更新版本”产生新版本 ID，旧消息、旧材料和旧证据仍保留原版；取消固定只移除项目关系，不删除历史。
- 工作文件的成果回执列表区分“查看当前版”与“引用记录版”。文件变化时，不会以新正文冒充旧写入 hash；从目录视图重新选择当前版本是显式新引用。

## 每轮上下文与连续对话

每个 Run 保存 `RunProjectContext`：项目 ID、名称、revision、说明正文和 hash。模型每个正常步骤读取同一份 Run manifest；自动压缩不删除它，因为 manifest 位于投影消息之外。修改项目说明不会打断执行、替换现有 Run 或暗中注入 steering 消息；新轮次才取当前项目设置。

固定材料的正文不自动塞进 prompt。模型只看到已发送引用的版本元信息，再用现有内置 `readMaterial` 按需读取，继续产生来源回执。项目内其他会话、目录全部文件和没有选中的材料不会自动进入上下文。

旧项目成员关系不会重写旧执行目录。完成后归到其他项目的会话，下一轮可以使用新项目的说明，但原目录绑定与写权限仍按既有规则检查，不转移到新项目目录。没有项目的旧 Run 仍兼容。

## 显式材料入口

输入 `@` 或点击 `@ 资源` 打开资源选择区，支持资源名称过滤、目录文件、成果和固定材料选择。选择只加入待发送引用，不发送消息、不覆盖草稿，也不授权资源的父目录；用户继续编辑后点击发送。

`@` 是选择入口，不是通过猜文件名展开正文的隐式命令。输入中的普通 `@` 文本保留；本版没有复杂的 inline mention parser、跨磁盘搜索或自动检索系统。

新任务准备票据保持既有 10 分钟有效期、重启失效的规则。已经附加到会话的版本和发送记录持久保存。项目说明未保存的编辑草稿不会宣称已成为执行上下文。

## 数据与 IPC

- `Resources.list` 是来源、版本与项目关系的投影，不建立另一套成果内容表。来源类型严格限制为 saved artifact、pin、projectFile、taskFile；不接受任意 renderer root、待审批提案或模型自造资源 ID。
- `projectFile` 读取必须通过已授权的项目根目录；`taskFile` 必须通过原会话目录与现有授权检查。pin 读取的是已明确固定的不可变归档，不读取当前磁盘。
- `projectContext/saveProjectInstructions/pinResource/updateProjectPin/listResources/openResource/prepareResource/attachResource` 是受信 renderer 的内置 IPC，不是新增模型工具或扩展注册接口。
- 保存项目说明和固定关系均使用 revision CAS；`ProjectStore.saveContext` 与项目更新时间在一个 SQLite 事务内提交。
- 项目归档拒绝修改上下文。目录授权撤销后，来源于该目录的固定版本仍可回看，更新必须重新满足原目录授权，不会自动改换新根目录。
- 新旧 material archive 都做 ID、字节数和 hash 检查；错误绑定或缺失版本在启动时失败关闭，不重建为“空项目”。

## 迁移与恢复

`projects.db` 从 schema 1 升到 2。升级前通过 SQLite `VACUUM INTO` 创建 `projects.db.before-context` 一致备份；新上下文表与 schema 标记在同一事务提交。旧项目默认空说明、无固定材料，不重写旧任务或历史正文。

旧 P1a 程序不认识项目 schema 2，会拒绝启动；回退不能仅替换程序继续写新数据库，需要保留完整 userData，并按版本恢复兼容备份。固定材料正文仍在 `tasks.db`，应同时备份，不应只拷贝 `projects.db`。

跨 `tasks.db` 与 `projects.db` 不是分布式原子事务：先保存不可变版本、再保存 pin 关系。中断或 CAS 失败可能留下未引用版本，但不会创建半授权项目引用或覆盖历史；本版不做自动清理这些版本。

## 参考与边界

轻量项目、多会话归类、文件列表先行及紧凑辅助区继续吸收 [NewMax 项目文档](https://newmax.cc/docs/features/projects)、[工作区文档](https://newmax.cc/docs/features/workspace) 与 [对话文档](https://newmax.cc/docs/features/chat) 的公开交互思路。未采用自动排期、后台记忆、默认完全访问或双工作台；公开文档对照不等同登录后的实机横评。

工作流仍以 Pi.dev、Codex、OpenCode 为既定参考，没有加入第三方扩展、MCP、插件市场、多模型、账单或自动 scheduler。沿用原文件自动快照、低打断授权、底部决策区与消息队列，不重新引入逐文件审批。

此处不是全量资源系统：不支持文件夹整体入模、Office/PDF 解析、网页固定包、跨会话正文自动共享、来源权威判断、语义检索、资源移动／删除管理或长期大库性能承诺。原生 Windows/macOS 的 CI fixture 不能代替签名安装、系统密钥存储或真实模型实机验收。

## 验收方式

`tests/resources-context.test.ts` 覆盖去重、版本更新、取消固定、权限撤销、坏引用、CAS、迁移备份和执行中说明冻结。`tests/e2e/preview.spec.ts` 验证选择不自动发送、草稿保留与共享资源 UI，预览仅使用示例数据。

`scripts/e2e-resources-context-native.mjs` 提供两条明确区分的路径。默认 `AGENT47_SMOKE` 使用模型 fixture 与显式测试工具意图，验证真实 Electron、IPC、数据库和文件归档；`AGENT47_RESOURCES_LIVE=1` 使用已批准的 HTTPS credential proxy 调用真实 DeepSeek，不注入模型、工具或数据库替身，只预设原生文件选择器的虚构测试材料。

真实路径要求先引用旧版与第一版项目说明，再显式更新固定版本与项目说明，删除源文件、重启、通过 `@` 加入新版本，生成成果并固定。检查实际读取回执、回复中的随机说明标记、成果中的随机材料标记和最终两条去重资源记录；每次实际结果在独立 JSON 中记录，不把 fixture 步骤数当真实模型结果。
